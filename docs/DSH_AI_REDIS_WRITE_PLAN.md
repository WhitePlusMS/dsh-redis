# DSH Redis：AI 写入 MVP 实施计划

更新日期：2026-11-11
状态：**MVP 已实现，验收进行中**。2026-11-11 根据用户要求调整为遵循 DSH 标准工具权限策略，不再要求证明每次批准来自人工点击。隔离 Redis、进程内工具管线及独立安装 Web profile 的合成会话已验证；完整浏览器对话和真实模型写入尚未验收，见[验证记录](verification/ai-write-mvp-2026-11-11.md)。

## 1. 目标和范围

用户通过 DSH 对话明确提出修改，AI 发起结构化提案；插件读取前态，遵循 DSH 的工具权限策略受控写入、回读，并将实际状态交给模型。宿主策略要求询问时由其决定交互方式；允许自动执行不代表已经人工审核。验收工具调用、服务器回执及回读，不以模型最终如何回答作为插件验收条件。

| 项目 | MVP 约定 |
| --- | --- |
| 操作 | 替换一个**已有 String** 的完整值，或一个**已有 Hash Key 中已有字段**的完整值。每次只改一个目标。 |
| 环境 | 先在自建隔离 Redis、独立 DSH profile 中使用合成数据验证；业务或生产使用需要另行授权和验收。写入默认关闭，由用户配置或受 DSH 权限保护的客户端入口显式启用，模型工具不能自行启用；启用状态绑定当前会话、连接代次和 DB，重连、切 DB、关闭或会话结束后失效。 |
| 版本和 TTL | MVP 暂定 Redis 7.4 或更高且命令语义经实测确认；Key 必须无 TTL，Hash 目标字段也必须无字段 TTL。无法检查、权限不足、版本或语义不确定时拒绝。此限制减少第一版的过期时间处理分支，不代表支持所有 Redis 兼容服务。 |
| 数据 | 插件必须提供完整、无歧义的目标和修改前后值；空字符串与不存在分开，二进制使用可核验的字节表示。超出插件资源或可提供的完整数据上限时拒绝；界面不得将截断内容冒充完整。自动允许不以人工查看界面为前提。 |
| 暂不做 | 创建 Key 或字段、删除、改 TTL、批量、多 Key、集合及模块类型、自由 Redis 命令或脚本、自动重试/撤销、持久化操作历史和生产部署。 |

这是首个可验证闭环，不代表后续只支持这两类数据。“写对”指插件按有效提案的目标和字节执行、检查并如实报告；不能保证 AI 理解了全部业务语义，也不保证结果之后不被修改或在故障切换后保留。

## 2. 项目与 DSH 接入

- 当前 [Redis 传输层](../src/host/redis-transport.ts) 只开放读取命令；[连接服务](../src/host/connection-service.ts) 按会话维护连接 ID、代次和 DB。写入走内部受控路径，不向模型开放自由命令，不破坏现有只读边界。
- 沿用 DSH 原生 `ctx.tools.register(defineTool(...))`，从 `exec.agent.session.id` 获取会话身份；模型不得指定会话、传入“已确认”或直接调用事务命令。Host 再次验证连接、DB、提案与授权。
- 本项目锁定 DSH `0.2.1-rc.5`。[工具管线](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.5/packages/core/tools/README.md)支持 `allow`、`ask`、`deny`；[approval 服务](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.5/packages/interaction/user-approval/README.md)的应答者可以是人或机器，`allowed-once` 不证明人工确认。现有查询范围确认不授予写入权限。
- 保留宿主策略的拒绝结果，不修改或绕过策略。工具参数、结果及宿主会话记录可能包含敏感值，不能仅靠隐藏预览就声称值不会进入模型或日志。

## 3. 单次操作流程

1. **明确目标**：用户明确当前连接、DB、准确 Key、Hash 字段（如有）和新值。目标或值有歧义时要求澄清，不扫描并猜测目标。
2. **读取前态**：Host 校验会话、连接 ID/代次和 DB，读取类型、存在性、完整旧值、Key TTL 和必要的字段 TTL。仅已有目标、无 TTL、插件能完整提供值时继续。
3. **生成提案**：Host 生成随机操作 ID，保存不可变的会话、连接代次、DB、Key/字段原始字节、旧值、新值、类型、无 TTL 前提及短有效期，返回完整提案供执行工具和策略审阅。
4. **宿主策略**：执行工具传入操作 ID 及完整提案，经过 DSH 原生工具执行管线；Host 在执行前逐项比对保存的提案。策略允许则继续，要求询问时按宿主流程处理，拒绝、取消或不可用均不写。不能把机器应答描述为人工批准。
5. **受控执行**：Host 单次消费提案，在连接独占期间按第 5 节 WATCH、重新比较和提交；前态变化或连接切换则终止，需要重新提案并再次经过宿主策略。
6. **回读并返回**：获得明确成功回执后，在同一服务器和目标读取实际值、类型及 TTL，逐字节对照预期。将第 6 节的结构化状态和必要事实交给模型及界面；不从模型回答推断写入结果。

## 4. DSH 原生权限策略

不另建审批系统，也不自行修改或绕过宿主策略。`tools/pre-execute` 由宿主及其插件决定允许、询问或拒绝；`ctx.tools.guard()` 只能增加拒绝。`ask` 的应答可能来自人或机器；用户已明确不要求每次点击“允许”。

1. 执行调用必须实际经过 DSH 工具管线。默认或策略 `allow` 只表示宿主放行，还须满足插件侧的写入启用、连接和提案校验才能执行；策略 `ask` 时由宿主审批服务处理，拒绝、取消或无应答者不得执行；策略 `deny` 不得被覆盖。审批服务的 `ask` 配置本身不代表所有工具都会被要求询问。
2. 策略需要查看实际目标时，执行工具参数须携带完整提案；Host 在调用体核对全部参数与同会话保存的不可变提案，且只允许消费一次。不能仅凭模型提供的操作 ID 或 `confirm: true` 免除核对。不得声称所有宿主界面必然展示完整内容：实际展示以隔离 profile 验证为准。
3. 验证 `allow`、`ask` 获准、拒绝、取消、无应答者及 `deny`；自动应答受宿主策略控制，不能称作人工确认。对话轮次结束、连接重建、切 DB 或提案过期后，未执行提案作废。
4. 连接身份、完整提案或单次消费无法验证时拒绝写入；预览、查询扫描确认和模型文本“好的”都不是独立授权。

实施前复核 DSH 的安装版本与调用链；示例或 mock 不能代替真实宿主验证。选择自动允许或机器应答的部署由宿主策略决定，用户应理解该模式不会逐次等待人工审核。

## 5. 并发和 TTL

优先验证现有连接的**连接级独占**：从 `WATCH` 到 `EXEC` 或 `UNWATCH` 结束前，不能混入 UI 读取、其他工具或 `SELECT`。若当前队列不能可靠实现独占和释放，先停止该路径，不急于增加第二套连接管理。

在同一物理连接依次执行：

1. 再校验会话、连接代次、DB 和单次授权，`WATCH` 目标 Key。
2. WATCH 后读取目标类型、存在性、完整旧值、Key TTL 及 Hash 目标字段 TTL，和提案时的前态比较；任何不一致、读取失败或权限不足均停止，不发送写命令。
3. 符合条件时执行 `MULTI`，只排入一条受控的 `SET` 或 `HSET`，再 `EXEC`；逐项解析事务回执。取消、异常或断线时清理；无法确认连接事务状态时关闭该连接，不能当作普通读连接继续复用。
4. WATCH 冲突时报告未执行，不自动重试；需要重新读取、生成提案并再次经过宿主策略。

**保证边界：**提案期间只比较目标值、类型、存在性和相关 TTL；同一 Hash 的其他字段若在 WATCH 前变化，不保证发现。WATCH 后同一 Key 的其他修改按 Redis 的 WATCH 语义触发冲突，须在隔离环境验证。WATCH 前发生“改掉又改回”的 ABA 历史也无法仅凭前后值发现；要求检测所有中间变化的业务需要另行设计可信版本机制。

MVP 只接受无 TTL 的目标：Key 的 `PTTL` 必须表示无过期；Hash 还需用服务器支持的字段 TTL 命令确认目标字段无过期。权限、版本或命令语义不明时拒绝。实际过期和淘汰行为须按目标版本验证；Redis 官方说明 6.0.9 之前 Key 过期不一定触发 WATCH，不能无条件声称旧版本具有同样保证。[Redis 事务](https://redis.io/docs/latest/develop/using-commands/transactions/) · [Hash 字段过期](https://redis.io/docs/latest/commands/hexpire/)

## 6. 写入结果状态和查询

MVP 在 Host **内存中保存有限操作记录**，按会话和随机操作 ID 隔离，供工具结果及界面只读查询。工具调用取消或连接断开不能立即删除已发出的操作记录。记录包括受控目标标识、阶段、时间、回执/错误分类和回读结果，不记录密码或完整值；操作 ID 在执行前作为提案数据提供，并随结果返回，不保证用户在自动模式下看到它。记录设容量及保留时间上限，实施时确定具体数值。过期后返回“记录不可用”，不能推断此前成功或失败。

| 状态 | 判定与含义 |
| --- | --- |
| 未执行 | 能确定提交命令未发出，例如策略未允许、前态不符或提交前取消。 |
| 冲突或明确拒绝 | Redis 明确返回 WATCH 冲突或命令拒绝；不重试。事务中的命令错误逐项判断，不能只凭 EXEC 外层有回复就报成功。 |
| 已写入并核对 | 收到明确成功回执，同一目标的回读值、类型和无 TTL 前提均符合预期；记录回读时间。 |
| 已写入，回读未确认 | 收到明确成功回执，但回读失败或被取消；不能说未写入。 |
| 已写入，回读不一致 | 收到明确成功回执，但回读值、类型或 TTL 不符；可能有后续并发修改，不能断言原因。 |
| 结果未知 | 提交命令可能已经发出，却没有得到可判定回执，例如发送后断线或超时；不能说成功或未写入。 |

提交前记录执行阶段；不能明确证明命令未发出时按“结果未知”处理。DSH 外层工具取消不等于 Redis 未执行：提交后 Host 在有界时间内继续收集回执/回读并更新记录；无法获得确定信息时标记未知，不能因调用方取消覆盖已有事实。

宿主仍运行且记录仍在时，用户可在当前会话用操作 ID 只读查询；查询本身不写 Redis。MVP 不做跨重启持久化：宿主崩溃或重启后记录不可恢复，也无法识别具体哪笔操作曾经未完成。重启后可展示通用提示“如果此前有未完成操作，其结果可能未知，请先检查 Redis 当前值”，不能伪造原操作状态。当前值只能辅助判断，不能证明丢失回执的请求是否执行过。未知状态禁止自动重放、自动回滚或换连接重试。

DSH 在进入执行工具前拒绝或取消时，插件执行体不会运行，也不会为本次调用创建新记录；应查看 DSH 对本次工具调用的拒绝或取消结果。按操作 ID 查询时，若没有同 ID 的既有记录则显示“记录不可用”；若已有记录，它只反映此前的执行，不能代表本次被拒绝的调用。

回读只证明该服务器在采样时的状态，不保证之后不变、业务语义正确或持久化/主从复制成功。

## 7. 实施和验收顺序

1. **验证 DSH 策略链路**：按第 4 节验证允许、询问与拒绝，真实隔离 profile 中核对所用部署的执行和展示；策略不能被绕过。
2. **验证 Redis 原子流程**：隔离 Redis 中验证连接独占、WATCH 前后比较、事务回执及无 TTL 限制，分别覆盖权限不足、类型变化和断线。
3. **实现最小闭环**：Host 提案、受控执行与内存结果记录；接入现有工具和界面，将结构化结果交给模型。原只读能力及宿主拒绝策略保持有效。
4. **真实链路验收**：使用合成数据和明确授权，核对：
   - 已有 String、已有 Hash 字段分别预览、经宿主策略执行、写入，并由独立只读客户端核对精确字节；`HSET` 返回 0 可能表示更新已有字段，不当成失败。
   - 写入未启用时，即使宿主放行或询问获准也不写；会话 A 的启用不适用于 B，禁用、重连或切 DB 后旧启用和提案均失效。
   - 策略拒绝、询问未获准、跨会话、提案被改、过期或重复执行均不写；机器应答按宿主策略处理，不能声称为人工确认。
   - 提案期间目标值变化，以及 WATCH 后目标或同 Key 其他字段变化，分别按第 5 节的边界验证；不声称检测 WATCH 前其他字段变化或 ABA。
   - 有 Key TTL、有字段 TTL、目标缺失、类型不符、版本/权限不符或插件无法提供完整提案均拒绝；空值与不存在不混淆。独立验证所测 Web profile 的展示，不声称所有宿主界面或用户均在执行前看到完整内容。
   - 提交前取消、提交后断线/取消、成功后回读失败或不一致、记录过期及宿主重启，逐项检查状态和查询边界；未知结果不自动重试。
   - 原有只读工具正常调用并返回结果；不以模型最终措辞判断插件是否成功。
5. 实施代码时再更新用户说明和 `UPDATE_LOG.md`，执行适当类型检查、测试、构建及隔离 profile 安装验证。生产环境、真实业务数据与发布不属于本计划自动授权范围。
