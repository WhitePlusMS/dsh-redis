# 多页面接收端与无接收端实测

日期：2026-11-06。工作区起点 `12727ad`；日常 DSH Web 沿用已安装应用源码 `622dce6`，安装基线见[拒绝验收记录](intent-and-rejection-2026-11-06.md)。本轮没有修改产品、模型配置或安装包。

## 结果

在日常 DSH / `bzkj-LLM` 中，两个独立页面同时承载同一会话时，打开 Redis 面板返回 `ambiguous`；关闭第二页后返回 `applied`。随后提交打开请求并立即关闭唯一验收页面，工具返回 `no_receiver`；重新进入会话后的新请求再次返回 `applied`。每轮仅一次 `redis_viewer_show {}`，没有重试或 Redis 查询工具调用。

本次继续使用[双面板验收](double-pane-2026-11-06.md)的只读会话，但该次合成 Redis 已停止，连接已断开。本轮无 Redis 夹具、没有保存连接资料或输入凭据。最终面板可见，状态为未连接；日常 DSH 3080 / PID10476 保持运行。

## 操作与证据

| 操作 | 原始工具结果 | 实际界面与模型表达 |
| --- | --- | --- |
| 原页面之外新开同一 DSH 地址，自动恢复同一会话，然后请求只打开一次 | `ambiguous`，当前对话有多个可接收的界面 | 原页面侧栏保持收起；模型没有声称已打开 |
| 关闭第二页，再次请求只打开一次 | `applied`，当前对话的 Redis 面板已确认可见 | 原页面实际打开 Redis 面板，显示未连接 |
| 提交打开请求后立即关闭唯一验收页面 | `no_receiver`，请在当前对话手动打开 Redis 侧栏后重试 | 浏览器标签清单为空；重新进入后看到这一已完成结果，模型说明不能确认打开且未重试 |
| 重新进入当前会话后发起新的打开请求 | `applied` | 新页面实际显示 Redis 面板且仍未连接，没有先手动打开面板 |

两个页面的同会话归属通过相同对话历史和本轮新消息同步核对。`03:52:05.766Z` 的只读 DOM 取证显示：原页面和第二页的 `document.visibilityState` 都为 `visible`；原页面没有可见 Redis 标签，第二页有一个 Redis 标签。因此本次不是在某一页面内同时挂两个 Redis 面板。

源码与观察对应：`src/client/index.ts` 在可见页面的当前会话注册动作通道，收起 Redis 侧栏不会退出整个会话通道；`src/host/ui-action-coordinator.ts` 在接收端数量不为一时分别返回 no_receiver/ambiguous。结合两个独立页面、各自至多一个面板及关闭第二页后恢复，证据支持多页面接收端保护；没有直接读取或修改 Host 内部集合，也没有伪造通道消息。

全关闭场景在发送后观察到生成中，再关闭页面；工具实际回执为 no_receiver。因此只能认定工具派发时无接收端，不能记作动作已经派发之后的 disconnected、执行之后回执丢失或 unknown。重新进入后的整轮显示 19 秒，包含模型和交互时间，不能当作界面动作超时。

模型本轮四次核心结果均与原始回执一致。最后一轮又括注 no_receiver“并非面板打开失败”，这应限于区分未找到接收端和接收端内部执行失败，不能解释成前次打开请求成功。工具及模型仍建议先手动打开侧栏，但本次重新进入后直接请求 show 即成功；这是一条可行的恢复路径，不证明必须先手动打开。已有 think 标题/正文问题未在本轮修复。
