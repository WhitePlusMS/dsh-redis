# Redis 企业公开案例：验收准备

日期：2026-11-05。以下仅核对公开一手资料并设计验收，**不是企业生产环境复现，也不是当前构建的验收通过记录**。真实 DSH、用户模型和数据的结果须在执行后另行登记；不得将本地数据或性能推断为企业实际情况。

## 美团广告信息和本地缓存

[美团技术团队：LruCache 在 DSP 系统中的应用演进](https://tech.meituan.com/2018/12/20/lrucache-practice-dsp.html)（2018）介绍以广告 ID 从 Redis 获取广告信息，并在应用侧引入本地 LruCache；文章还讨论 Redis 数据变化时本地缓存可能不及时更新。

- 验收问题：给出明确的合成广告 Key，询问 Redis 当前值和 TTL；再询问缺失对象的原因以及应用本地缓存是否一致。
- 预期证据：当前连接、DB、采样结果与时间；缺失仅说明采样时不存在，不能判断历史上是否过期或从未写入。仅有 Redis 采样不能证明应用进程的本地缓存一致或不一致。
- 当前构建 `1375e2f` 的本地缓存问题：日常 DSH、`bzkj-LLM` 和用户 Redis 中要求只读取一个明确 Key 的类型和 TTL，判断应用进程本地缓存与 Redis 是否一致；模型只调用一次 `redis_viewer_key_metadata`，未读取值，正确说明缺少两侧值和应用侧采样，不能判断一致性。工具返回非快照，但模型将类型和 TTL 表述为同一时刻的确定事实，并在后续建议中引用旧对话的一个业务字段；这些表述不应扩大为本轮实际读取或原子采样。未修改用户数据，不记录业务 Key、字段和值。此前同一模型会话的模糊缺失问题还给出以 TTL 区分历史原因的错误建议；合成广告对象及缺失问题尚未按本案例完整复验，**整个案例尚未通过**。

## 美团扫描与 Rehash

[美团技术团队：Redis Rehash 机制的探索和实践](https://tech.meituan.com/2018/07/27/redis-rehash-practice-optimization.html)（2018）记录过历史版本字典收缩时扫描遗漏桶、影响清理完整性的缺陷，并说明所讨论源码基于 Redis 3.2.8，修复已合并。该案例不能作为当前版本仍存在该缺陷的证据。

- 验收问题：用户明确给出 Key 名称模式，要求按批查看候选并解释续读和覆盖范围。
- 预期证据：逐批游标和计数、完成状态、非快照及并发变化限制；MATCH 过滤结果不保证避免遍历当前 DB 键空间。核对现有环境的行为，不执行案例中的删除、清理或负载操作。
- 当前构建 `1375e2f` 的单批复验：日常 DSH、`bzkj-LLM` 和用户 Redis 中，明确指定一个名称模式且只请求首批；模型调用一次 `redis_viewer_keys`，空页、非空游标和未完成状态与工具一致，正确说明空页不代表不存在、MATCH 不保证只遍历匹配名称、跨批非快照。回答把 COUNT 100 描述为每次约遍历 100 个槽位，比工具提供的工作量提示更具体，不能据此保证每次扫描的具体工作量。此前真实模型曾完成续读但误计批次数；当前构建的模糊问题还出现未经澄清即猜测模式并扫描。**单批主要范围说明通过，完整案例仍未通过。**本次未读取值或修改数据，不记录业务名称。

## GitHub Redis 认证故障

[GitHub 2023 年 2 月可用性报告](https://github.blog/news-insights/company-news/github-availability-report-february-2023/)（2023）说明一次 Redis 启用认证后，容器镜像仓库的生产部署使用硬编码连接串，客户端无法认证；故障通过回退认证配置恢复。

- 验收问题：独立 Redis 的受限连接资料认证失败时，请模型解释当前连接状态和可确认的事实。
- 预期证据：工具的认证失败分类及旧连接状态；不能仅凭失败断言密码、连接串、服务端配置或 GitHub 同一根因。不得记录凭据，测试完成恢复原连接。
- 当前构建 `1375e2f` 的隔离复验：日常 DSH、`bzkj-LLM` 与独立 Redis 8.2.6；原用户 Redis 连接活动时，以不含密码的临时资料尝试连接受限测试账号，工具返回 `failed/auth`，模型说明需要本地处理凭据并报告原连接仍连接。随后另发明确只读请求，成功读取原连接一个 Key 的类型与 TTL，进一步证明该次认证失败后原连接仍可执行这一读取；首次回答时仅有状态信息，还没有这次读取证据。该场景未证明其他认证失败、取消、超时或候选套接字释放，也未复现 GitHub 的部署配置。临时资料删除；隔离 22 个 Key 的 DUMP、绝对过期时间和数量未变，实例已停止；未修改用户 Redis 数据或记录业务身份。

## 美团高负载与网络丢包

[美团技术团队：Redis 高负载下的中断优化](https://tech.meituan.com/2018/03/16/redis-high-concurrency-optimization.html)（2018）从网络丢包监控出发，结合操作系统和网卡指标分析接收队列、中断处理等因素。

- 验收问题：询问当前 Redis 状态、慢日志能否说明应用请求变慢，及是否足以判断网络丢包或中断瓶颈。
- 预期证据：只列实际取得的 Redis 指标、采样时间及慢日志保留范围；Redis 采样不能单独证明网络、网卡或操作系统中断的根因，需要相应系统及业务侧证据。
- 当前构建 `1375e2f` 的案例对话：日常 DSH、`bzkj-LLM` 和用户 Redis 上询问应用变慢是否由网络丢包或系统中断造成；模型调用 `redis_viewer_overview` 的 `server` 和 `stats`、`redis_viewer_slowlog` 的最近三条（实际一条），说明单次 Redis 采样不足以判断网络或系统根因，并列出需要其他系统指标。但它进一步承诺可只读查询指定时段的慢日志及延迟事件；当前插件的慢日志工具只返回最近有限条，未提供按时段查询或延迟事件工具，该能力承诺不准确。**诊断边界部分正确，完整回答未通过。**未在用户 Redis 上制造高负载或修改数据、配置，未记录业务指标。
