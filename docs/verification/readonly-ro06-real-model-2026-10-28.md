# 当前插件构建的真实 DSH 模型验证

日期：2026-10-28。此记录是阶段 1 的部分真实对话证据，不能替代 RO06 全项验收。

## 环境

- 在用户现有 DSH home 下创建唯一临时 profile `redis-eval-01a181a4`，从 Web 模板初始化并仅向该 profile 安装本项目包；共享用户现有模型凭据存储，不读取或记录凭据。日常 `web` profile 未安装本次包。
- 首次 `--dump-config-schema` 初始化时 DSH 报告未识别的 Loader tree carrier，命令以失败退出但已建立 profile；随后该 profile 成功安装包、启动 Web、注册 Redis Host 并完成真实模型调用。schema 报错未被当作通过。
- 真实模型为 DeepSeek-V41-Flash，会话访问模式“仅可查看”。临时 profile 与现有 DSH home 共享工作区和会话列表；本次创建的新测试会话保留在共享历史中，未读取或删除其他会话。
- Redis 为自建的短时本机测试实例，包含 140 个合成 String Key 与一个合成 Hash；用户已有 Redis 不作业务写入。验收后回读全部 140 个 String 值、Hash 字段和 DB 1，均与预置状态一致。

## 真实对话与工具轨迹

1. 包 SHA-256 `415840c2c031eb09246b1bcc5d94839eb34c259a417d7126d4c0fe13a979d2b8` 与当时项目构建的 AI reader 一致。模型调用 `redis_viewer_status` 和两次 `redis_viewer_keys`，第二次使用相同 `order:*` 与首批返回的 cursor；两批分别返回 100 和 41 个 Key，末批 `cursor: null`、`scanComplete: true`，模型报告 141 个，与夹具一致。
2. 用户界面选中合成 Hash `order:details` 的 `status` 字段后，模型调用状态工具和无参数 `redis_viewer_value`；实际结果标明 `source: selection`，返回 `synthetic-ready`，与夹具一致。
3. 明确要求切换 DB 1 后，轨迹显示 `redis_viewer_select_db` 参数 `{"db":1}` 和随后的 `redis_viewer_status`；工具及侧栏显示 DB 1、原选中项失效。
4. 此次模型最初把 generation 递增解释成物理连接重建，工具返回的连接 ID 实际未变，不能支持这一推断。指出证据后模型承认并更正。随后修改 `redis_viewer_status` 和 `redis_viewer_select_db` 的工具描述，明确 generation 只是插件连接/DB 视图版本，不能凭它推断物理重连或服务器重启。
5. 重新打包 SHA-256 `55a8b20cb0f00bda5a6ad57b35427804c0fcdad43cea25537d6248c69ee6f49f`。使用新对话、同一临时 profile 和合成 Redis 再次请求切换 DB 1，真实模型调用切库和状态工具，回答明确说 generation 递增不代表物理连接重建。此次复测是一次样本，不能保证模型未来永不误判。

## 2026-10-30：日常模型和当前包装配复核

- 日常 `dsh web` 新会话中的默认 DeepSeek 模型普通消息再次重试 5 次失败；切换到日常已配置的 `bzkj-LLM` 后，真实普通消息成功。切换发生在验证会话中，不能据此称默认 DeepSeek 的连接重置已经修复。
- 日常原有 Redis 包与当前构建不同：对照其安装包的 62 个 `lib` 文件，27 个与当前构建不一致。该旧包上，真实模型调用 `redis_viewer_status` 和 `redis_viewer_keys`，独立合成 Redis 的一页实际返回 101 条并带续读令牌。
- 旧包另一会话的分页轨迹经展开数组逐项计数，第一页 101 条，第二页 40 条，最后游标为空且扫描完成；模型报告为 100、39、总计 139，和实际 141 条不一致。此为真实模型总结误差，不当作当前构建分页验收通过。

## 2026-10-30：真实在途取消及阶段结论

- 隔离验收包 `a5e6bf6ec77327e7e2d332f1d098514c6879ca60842a783d4a839bd6d3387240` 与先前 `55a8b20cb0f00bda5a6ad57b35427804c0fcdad43cea25537d6248c69ee6f49f` 的 `lib` 文件对比，仅 `host/ai-key-pages.js` 不同，变化为本批计数；先前包的字段读取、切 DB、目标变化和跨会话证据仍按各自包哈希记录。
- 在当前包真实 DSH 会话中，延迟代理捕获合成 `order:000` 的 `GETRANGE` 并扣留响应后，立即点击“停止生成”。轨迹显示 `redis_viewer_value` 以错误结束，耗时 1,223 毫秒，早于 transport 的 10 秒超时；释放延迟响应后，本轮保持停止，未显示成功值。轨迹只显示 `Error: [object Object]`，没有直接显示底层 AbortSignal 或错误码，因此不推断更细的内部传播细节。
- 同一连接在释放响应后，原生面板再次读取该合成 Key，显示完整预置值。此检查证明这次受控交错后可继续读取，不代表所有取消与网络时序均已覆盖。之前一次代理响应先超时、随后才停止生成的尝试不计为取消通过。
- RO06 按清单条件完成：分开归档类型/完整打包测试、隔离 Redis、原生 DSH、真实模型的无连接、分页及续读、选中字段、切库与目标失效、跨会话和取消证据；预算耗尽后人工恢复及原游标续读也已实测。默认 DeepSeek 连接重置仍未解决，真实模型验收使用日常已有 `bzkj-LLM`，不能扩大为所有模型均可用。
