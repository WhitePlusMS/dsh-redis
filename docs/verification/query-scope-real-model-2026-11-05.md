## 诊断及公开案例的证据边界

`14:24:37.407–.451Z` 实际进行了六次调用：缺失 Key 元数据、单 Key 内存、Stream 消费组、overview(server)、overview(clients)、slowlog(count=5)。这里客户端概况使用的是 overview 的 clients 节，不能记成 `redis_viewer_clients` 明细工具验收。

- 缺失 Key 为 missing，TTL 与类型为 null。模型明确不能证明历史过期或应用本地缓存不一致。
- 内存结果 64 字节，请求 SAMPLES 5、实际采样数 null；模型正确说明实际项数未知、可能含内部碎片、不是服务器总内存。
- 消费组 1 个，pending=1、lag=1、entriesRead=1、consumers=1；模型数字一致且没有消费操作，但错误声称“不消费便无法产生第二、第三个观测点”。重复只读采样并不要求消费消息。
- 服务器概况为 Redis 8.2.6、uptime 899 秒；客户端概况为 connected_clients=2、blocked_clients=0，均为这次合成实例的采样，不代表用户环境。
- 请求最多 5 条慢日志，返回 3 条，原始 UTC、微秒耗时和命令名与模型复述一致；没有返回参数、客户端地址或名称。模型仍无依据地将其中一条 JSON.GET 归因到具体 Key 和“大 payload”，不能据时间相近完成归因。
- 模型明确 Redis 这些采样不能证明网络丢包或中断瓶颈，但附加归因及消费组解释错误，整体诊断回答未通过。没有保存诊断报告。
