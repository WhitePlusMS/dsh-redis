## 取消语义核对

前一轮在独立 Redis 2955 / 代理 3051 中，确认 GETRANGE 响应暂扣后点击取消，界面立即停止、工具返回 stale，连接到约 10 秒时才关闭。该现象最初被列为待诊断，不能直接认定取消信号丢失。

当前 `src/host/redis-transport.ts` 的既有约定是：取消立即结束调用者等待；已发送命令的有界响应仍需接收完，之后才发送下一命令，防止 RESP 响应错配；原期限内未收到完整响应才关闭连接。这与现行方案“停止等待不等于撤回命令”一致，不要求每次取消都立即断开 Redis。

临时 `check-http-cancel.mjs` 使用已安装 DSH Connection 的真实 HTTP 客户端与 Host 桥接代码、项目 String 读取器以及合成 RESP 对端。HTTP 取消到达宿主，读取约 3.78 毫秒后返回 failed/cancelled，连接保留以接收旧响应；释放旧响应后，已取消读取没有发送后续 TYPE/STRLEN/PTTL，另一个明确排队的 TYPE 正确得到自己的响应。该脚本不经过浏览器 UI 或 Gateway 描述符绑定，不替代下述日常 Web 验收。首次运行仅清理 API 写错，修为 Cordis fiber.dispose 后退出 0。

既有传输专项中，取消后完整/分片响应接收、取消队列不派发、活动请求超时关闭四项通过（其余 19 项未在本次命令执行）。没有据此增加取消协议或修改 SDK。

本轮严格类型检查和文档 diff 检查通过；未重复运行未变产品的完整打包测试。

## 真实页面与模型

独立 Redis 8.2.6 / 3386，22 条合成数据；代理 11997 仅暂扣 fixture:string 的下一次 GETRANGE 真实响应。沿用有历史错误回答的同一验收对话，每轮发送同一请求：仅刷新当前选中界面一次、按实际回执说明、不额外查询/扫描/重试/重连。先确认响应已暂扣和界面处于读取中，再操作。

三轮均只调用一次 redis_viewer_refresh，模型如实报告未确认刷新及读取可能已发出，没有把旧预览或新 List 的读取说成原刷新成功，没有自动重试、重连或追加模型查询。模型将 stale 概括为“过期或失效”，不能由该词确定具体是哪一种用户操作。

重新展开侧栏会正常加载 DBSIZE、INFO、CONFIG GET databases 和 SCAN；“不自动续读旧值”不能扩大成“完全没有 Redis 请求”。手动切 Key 也会读取新目标。本轮没有开启自动刷新。旧预览保留并不证明本次刷新完成。

正式三轮之前另有一次测试等待器未识别暂扣状态，未执行到取消，实际返回 timeout 并在期限关闭连接 1。它只记录为超时，不能计入取消通过。改为显式传入证据目录后完成上表三轮；该调整只在临时 CUA 诊断代码中。
